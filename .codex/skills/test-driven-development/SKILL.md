# Test Driven Development

## FrontMatter

- 실행 조건: 승인된 요구사항의 코드·테스트 구현
- 실행하지 않는 조건: 요구사항이 확정되지 않았거나 단순 설명만 요청된 경우

## Input Contract

- 승인된 요구사항과 수용 조건
- 불변식과 상태 전이
- 관련 코드와 테스트
- 적용할 아키텍처·컨벤션
- 테스트 전략

## Steps

1. 관련 아키텍처 컨벤션과 테스트 규칙을 필요한 범위에서 확인한다.
2. 테스트 대상 계층과 테스트 대역 사용 범위를 결정한다.
3. 하나의 행위나 규칙을 검증하는 실패 테스트를 작성한다.
4. 의도한 이유로 실패하는지 확인한다.
5. 테스트를 통과시키는 최소 구현을 작성한다.
6. 관련 테스트와 기존 테스트를 실행한다.
7. 중복과 책임을 정리한 뒤 다시 검증한다.
8. Repository·트랜잭션·실제 DB가 대상이면 실제 기술 통합을 검증한다.

## Output Contract

- 변경된 프로덕션 코드
- 변경된 테스트
- 테스트 실행 결과
- 적용한 설계 판단
- 남은 위험과 미완료 항목

## Verification Gate

- [ ] 요구사항별 테스트가 존재하는가?
- [ ] RED와 GREEN 결과를 확인했는가?
- [ ] 정상·예외·경계 조건을 검증했는가?
- [ ] 관련 기존 테스트를 실행했는가?
- [ ] 실제 기술 동작을 Mock으로 대체하지 않았는가?

## Failure Policy

- 실패 원인이 요구사항인지 구현인지 구분한다.
- 테스트 실패를 숨기거나 기대 결과를 임의로 바꾸지 않는다.
- 같은 원인의 실패를 반복하지 말고 원인을 수정한 뒤 재실행한다.
- 세 번의 반복 후에도 실패하면 원인과 필요한 결정을 사용자에게 보고한다.

## Exit Criteria

- 승인된 요구사항이 테스트와 구현에 반영되었다.
- 관련 테스트가 통과했다.
- 코드와 테스트가 적용할 아키텍처 규칙을 지킨다.
- 미완료 항목과 위험이 보고되었다.

## Anti-Rationalization

- 테스트를 먼저 통과시키기 위해 요구사항을 약화하지 않는다.
- 테스트가 통과했다는 이유만으로 누락된 불변식을 완료로 간주하지 않는다.
- 필요한 아키텍처 문서 확인을 생략하지 않는다.
- 통합 동작이 필요한 대상을 단위 테스트만으로 완료 처리하지 않는다.
