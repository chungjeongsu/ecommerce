# Documentation and ADRs

## FrontMatter

- 실행 조건: 승인된 설계 결정이나 새로운 규칙을 관련 문서에 반영해야 할 때
- 실행하지 않는 조건: 문서 변경이 요청되지 않았고 코드·테스트와 기존 문서가 일치하는 경우

## Input Contract

- 승인된 요구사항과 설계 결정
- 변경된 코드와 테스트
- 관련 도메인·아키텍처·테스트 문서
- 문서 변경 범위

## Steps

1. 코드·테스트·기존 문서 사이의 불일치를 확인한다.
2. 변경 내용을 도메인 규칙, 아키텍처 결정, 테스트 전략, 작업 절차로 분류한다.
3. 가장 직접적으로 연결된 문서를 선택한다.
4. 승인된 내용만 명확하고 중복 없이 반영한다.
5. 문서 간 모순과 링크를 확인한다.
6. 변경 내용을 요약하고 남은 불일치를 보고한다.

## Output Contract

- 수정한 문서 목록
- 문서별 반영 내용
- 확인한 코드·테스트 범위
- 남은 불일치
- 승인이 필요한 사항

## Verification Gate

- [ ] 변경 근거가 코드·테스트·승인된 요구사항에 있는가?
- [ ] 가장 적절한 문서에 반영했는가?
- [ ] 동일한 규칙을 불필요하게 중복 기록하지 않았는가?
- [ ] 미승인 비즈니스 규칙을 확정하지 않았는가?
- [ ] 문서 간 모순이 없는가?

## Failure Policy

- 문서와 코드가 충돌하면 어느 쪽도 임의로 정답 처리하지 않는다.
- 새로운 비즈니스 규칙은 사용자 승인 전까지 문서에 확정형으로 기록하지 않는다.
- 문서 위치가 불명확하면 관련 문서 구조를 확인한다.

## Exit Criteria

- 승인된 변경이 관련 문서에 반영되었다.
- 문서·코드·테스트의 정합성이 확인되었다.
- 남은 불일치와 승인 필요 사항이 보고되었다.

## Anti-Rationalization

- 구현했다는 이유만으로 문서를 자동 수정하지 않는다.
- 문서 변경을 줄이기 위해 새로운 규칙을 생략하지 않는다.
- 문서의 빈틈을 임의의 도메인 규칙으로 채우지 않는다.
