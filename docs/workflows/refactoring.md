# Refactoring Workflow

## 입력

기존 동작은 유지하면서 개선하려는 구조적 문제나 목표를 자연어로 설명한다.

예시: `결제 승인 로직의 책임을 분리하고 구조를 개선해줘.`

`/refactoring {도메인 또는 파일} {개선 목표}` 형식은 Workflow를 직접 지정하는 축약 표현으로 사용할 수 있다.

## 목표

기존 기능과 도메인 불변식을 유지하면서 구조적 문제를 개선한다.

새로운 기능이나 비즈니스 규칙을 추가하지 않는다.

## 실행 절차

### 1. 대상 분석
- 관련 정책 및 도메인 문서 확인
- 대상 코드와 호출 관계 탐색
- 관련 테스트 확인
- 중복, 과도한 책임, 높은 결합도 등 구조적 문제 식별

### 2. 동작 보존 기준 확인
- 현재 외부 동작 및 계약 확인
- 기존 테스트 실행
- 보호되지 않은 주요 동작이 있다면 특성화 테스트 추가

현재 동작이 요구사항과 충돌하면 임의로 보존하거나 수정하지 말고 사용자 판단을 요청한다.

### 3. 변경 계획
- 개선할 구조적 문제 정의
- 변경 범위 최소화
- 클래스·메서드·의존 관계의 변경 계획 작성
- 외부 계약이나 아키텍처 경계 변경이 필요한 경우 정책에 따라 승인 요청

### 4. 점진적 리팩터링
- 작은 변경을 하나씩 적용
- 변경 후 관련 테스트 실행
- 실패 시 원인 확인 및 수정
- 불필요한 추상화 추가 금지

### 5. 최종 검증
- 기존 테스트 재실행
- 외부 동작 및 공개 계약 유지 확인
- 도메인 불변식 유지 확인
- 성능이나 동시성에 영향이 있는 변경은 필요한 추가 검증 수행

### 6. 문서 정합성
- 책임 또는 구조 변경이 기존 문서에 영향을 주는지 확인
- 승인된 구조 변경만 관련 문서에 반영
- 비즈니스 규칙 변경이 필요하면 리팩터링 범위를 벗어난 사항으로 보고

## 완료 결과

1. 개선한 구조적 문제
2. 변경된 코드
3. 동작 보존 검증 결과
4. 문서 변경 내역
5. 남은 위험 및 후속 작업
