# Implementation Workflow

## 입력

구현할 기능이나 유스케이스를 자연어로 요청한다.

예시: `주문 생성 기능을 구현해줘.`

`/impl {도메인} {구현할 유즈케이스}` 형식은 Workflow를 직접 지정하는 축약 표현으로 사용할 수 있다.

## 목표

승인된 요구사항과 불변식에 따라 유즈케이스를 TDD로 구현하고 검증한다.

## 실행 절차

### 1. 구현 준비
- 공통 정책 및 관련 도메인 문서 확인
- 기존 구현과 테스트 탐색
- 정상·예외 흐름 확인
- 필수 미확정 규칙이 있는지 검토

구현에 필요한 비즈니스 판단이 미확정이면 해당 부분은 사용자 승인을 받는다.

### 2. 테스트 계획
- 유즈케이스를 작은 테스트 케이스로 분해한다.
- 정상 흐름, 경계 조건, 예외 흐름을 포함한다.
- 관련 불변식과 상태 전이를 테스트에 대응시킨다.
- 구현 순서를 정한다.

### 3. TDD 루프

각 테스트 케이스마다 다음 과정을 반복한다.

**RED**
- 하나의 동작이나 규칙을 검증하는 테스트 작성
- 실행하여 의도한 이유로 실패하는지 확인

**GREEN**
- 테스트를 통과시키는 최소 구현 작성
- 기존 테스트와 신규 테스트 실행
- 승인되지 않은 비즈니스 규칙 추가 금지

**REFACTOR**
- 중복 제거 및 책임 개선
- 외부 동작과 불변식 유지
- 관련 테스트 재실행

다음 테스트 케이스로 이동하며 반복한다.

### 4. 테스트 전략
- Domain: 실제 도메인 객체 우선
- UsecaseImpl: 필요한 의존성만 Mock/Stub 사용
- Repository: 실제 DB 통합 테스트
- Aggregate 협력: 필요한 통합 테스트
- 외부 시스템: HTTP Stub 또는 Mock 서버
- Fake: 필요성이 확인된 경우에만 도입

### 5. 통합 검증
유즈케이스 수준에서 다음을 검증한다.

- 정상 및 주요 예외 흐름
- Aggregate 간 협력
- 데이터 정합성 및 트랜잭션
- 멱등성과 중복 요청
- 필요한 동시성 시나리오

테스트 실패 시 원인을 분석하고 같은 구현 루프 안에서 수정한다.

### 6. 문서 피드백
구현 중 새로 발견한 사항을 식별한다.

- 새로운 불변식과 상태 전이
- 새로운 Aggregate 간 관계
- 기존 문서와 코드의 불일치
- 새로운 아키텍처 결정

승인이 필요한 사항은 임의로 결정하지 않는다.

승인된 규칙의 변경은 관련 문서에 반영한다.

### 7. 완료 검증
- 요구사항과 테스트 케이스 대조
- 관련 테스트 실행 및 결과 확인
- 누락된 주요 예외 흐름 확인
- 미완료 사항 및 남은 위험 기록

## 완료 결과

1. 구현한 기능
2. 작성·수정한 테스트
3. RED/GREEN 확인 및 최종 테스트 결과
4. 변경된 프로덕션 코드
5. 문서 변경 내역
6. 미확정 사항 및 남은 위험

모든 검증이 끝나지 않았다면 완료로 보고하지 않는다.
## 계층별 구현 분기

`/impl`은 모든 작업에 동일한 단계를 강제하지 않는다. 대상 계층을 식별한 뒤 해당 계층의 구현·테스트·검증 범위를 선택한다.

### 공통 흐름

1. 요구사항과 불변식을 확정한다.
2. 변경 영향 범위를 작성한다.
3. 대상 계층의 규칙에 맞게 구현한다.
4. 계층에 맞는 테스트를 작성하고 실행한다.
5. 전체 변경사항을 리뷰한다.
6. 컴파일 및 필요한 테스트를 검증한다.

### Domain

- Entity, Value Object, Aggregate의 불변식을 확인한다.
- 상태 전이와 도메인 행위를 테스트한다.
- Aggregate Root가 내부 객체의 생성과 변경을 관리하는지 확인한다.
- 외부 기술 없이 도메인 단위 테스트를 우선한다.

### Application

- Usecase의 입력·출력 계약과 실행 흐름을 확정한다.
- Port 호출 순서, 트랜잭션 경계, 권한 및 실패 흐름을 확인한다.
- Repository와 외부 API는 Mock 또는 Stub으로 격리한다.
- 정상 흐름, 실패 흐름, Port 호출 계약을 테스트한다.

### Persist

- Entity 필드와 연관관계를 설계한다.
- `mappedBy`, `@JoinColumn`, cascade, orphan removal 설정을 확인한다.
- Repository 저장·조회 동작을 구현한다.
- Flyway 스키마와 Entity 매핑, 제약조건을 일치시킨다.
- 실제 테스트 DB를 사용하는 Repository 통합 테스트를 작성한다.

### Presentation

- 요청·응답 계약과 입력 검증을 확정한다.
- Controller의 Usecase 호출과 응답 변환을 구현한다.
- 정상 응답, 요청 검증 실패, 도메인 예외의 HTTP 매핑을 테스트한다.

## 완료 기준

- 대상 계층에 필요한 구현과 테스트가 모두 반영되어야 한다.
- 관련 Entity, 연관관계, Repository, Flyway가 변경된 경우 서로의 매핑을 함께 확인한다.
- 테스트를 실행하지 못한 경우 성공으로 보고하지 않고 원인과 검증 범위를 기록한다.
- 다른 계층에 영향을 주는 변경은 해당 계층의 검증을 추가한다.
