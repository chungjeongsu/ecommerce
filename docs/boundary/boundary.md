# Agent Boundaries

## 1. 요구사항 판단

### Always
- 요구사항을 분석하고 모호하거나 누락된 비즈니스 규칙을 식별한다.
- 요구사항의 모호함이나 누락이 의심되면 관련 문서와 기존 코드를 먼저 조사한다.
- 조사 후에도 판단이 불가능할 경우 Ask First로 권한을 변경한 후 사용자에게 승인을 받는다.

### Ask First
- 새로운 비즈니스 규칙을 확정하거나 기존 API 동작을 변경하기 전에 사용자 승인을 받는다.
- 승인 전 사용자 이해를 목적으로 설명을 자세하고 이해하기 쉽게 설명한다.

### Never
- 명시된 도메인 불변식을 임의로 변경하거나 무시하지 않는다.
- 도메인 문서는 임의로 수정하지 않는다.

## 2. 설계 판단

### Always
- 구현 전에 기존 아키텍처와 설계 의도를 분석한다.

### Ask First
- 새로운 기술을 도입하거나 기존 아키텍처를 변경하기 전에 사용자 승인을 받는다.
- 승인 전 사용자 이해를 목적으로 설명을 자세하고 이해하기 쉽게 설명한다.

### Never
- 승인 없이 핵심 설계 원칙을 위반하거나 기존 설계 결정을 무시하지 않는다.

## 3. 기술적 권한

### Always
- 허용된 작업 범위에서 필요한 파일을 읽고 변경 사항을 확인한다.
- 허용된 작업 범위를 식별할 수 없거나 애매할 시 Ask First로 권한을 변경한 후 사용자에게 승인을 받는다.
- 기술적으로 불가능한 작업 범위일 시 원인을 조사 후 추가 권한 필요 시 Ask First로 권한을 변경한 후 사용자에게 승인을 받는다.

### Ask First
- Git push, 운영 DB 변경, 외부 시스템에 영향을 주는 명령을 실행하기 전에 사용자 승인을 받는다.
- commit은 사용자가 명시적으로 요청한 경우에만 수행한다.
- push는 commit과 별도로 사용자의 명시적인 요청이 있을 때만 수행한다.
- 승인 전 사용자 이해를 목적으로 설명을 자세하고 이해하기 쉽게 설명한다.

### Never
- 비밀키를 노출하거나 허가되지 않은 파일 및 시스템에 접근하지 않는다.

## 4. 검증 판단

### Always
- 코드 변경 후 관련 테스트를 실행하고 결과를 확인한다. 문서만 변경하는 경우에는 관련 문서 간 정합성을 검증한다.
- 3회의 반복 이후 테스트가 계속 실패 시 Ask First로 권한을 변경한 후 사용자에게 승인을 받는다.

### Ask First
- 테스트의 기대 결과나 기존 완료 기준을 변경하기 전에 사용자 승인을 받는다.
- 승인 전 사용자 이해를 목적으로 설명을 자세하고 이해하기 쉽게 설명한다.

### Never
- 실패한 테스트를 은폐하거나 검증하지 않은 결과를 성공으로 보고하지 않는다.

## 5. Default Policy
- 허용된 작업 범위에서는 코드 탐색, 구현, 테스트 및 재시도를 자율적으로 수행한다.
- 명시되지 않은 행동은 실행 전에 영향 범위를 분석 후 사용자에게 승인을 받는다.
- 되돌리기 어렵거나 외부 시스템에 영향을 주는 작업은 사전에 승인받는다.
- Never와 Ask First 규칙은 일반적인 자율 실행 권한보다 우선한다.
- 사용자의 승인이 필요한 경우 문제 정의, 발생 원인, 영향 범위, 해결 방안, 권장 방안을 사용자 이해를 목적으로 자세하고 이해하기 쉽게 설명한다.
- 승인 전에는 해당 변경을 실행하지 않는다.

## 6. Workflow와 탐색 경계

### Always
- 자연어 요청의 목적과 범위를 분석해 가장 적절한 Workflow를 선택한다.
- 작업을 시작하기 전에 선택한 Workflow와 대상 범위를 사용자에게 확인한다.
- Workflow 확인 후 해당 Workflow와 직접 관련된 문서·코드·테스트만 선택적으로 탐색한다.
- 분석 결과와 실제 변경을 구분해 보고한다.

### Ask First
- 한 요청에 여러 Workflow가 필요하고 우선순위가 불명확하면 사용자에게 순서를 확인한다.
- 분석 요청이 변경 요청으로 확대될 가능성이 있으면 변경 전에 사용자 승인을 받는다.
- 문서 간 충돌을 발견하면 어느 문서를 정답으로 볼지 사용자에게 확인한다.

### Never
- 자연어 요청을 임의로 구현 작업으로 확정하고 바로 변경하지 않는다.
- 분석·리뷰·요구사항 검증 Workflow에서 승인 없이 프로덕션 코드나 도메인 문서를 변경하지 않는다.
- 관련 없는 문서와 전체 코드베이스를 무차별적으로 읽지 않는다.

## 7. 점진적 요구사항 확인

### Always
- 미확정 사항은 영향 범위가 큰 항목부터 하나씩 확인한다.
- 사용자의 답변을 관련 문서에 반영한 뒤 다음 항목으로 진행한다.

### Ask First
- 여러 미확정 사항을 동시에 질문하지 않는다.
- 사용자가 `다음`이라고 하면 현재 질문을 보류하고 다음 우선순위 항목을 질문한다.

### Never
- 한 번의 응답에 긴 미확정 사항 목록을 제시해 사용자의 판단을 요구하지 않는다.
