# 테스트 코드 컨벤션

## 목적

이 프로젝트는 도메인 규칙과 유스케이스를 테스트로 먼저 명세하고, 테스트를 기준으로 구현을 진행하는 TDD를 따른다.

테스트는 구현 세부사항보다 다음을 검증하는 데 목적이 있다.

- 도메인 객체와 Aggregate의 불변식
- Application Usecase의 실행 흐름
- Persist와 Infra의 실제 기술 연동
- Presentation 진입점의 외부 통신

## TDD 흐름

기능 구현은 다음 순서로 진행한다.

```text
요구사항과 불변식 확인
        ↓
실패하는 테스트 작성
        ↓
최소 구현
        ↓
테스트 통과
        ↓
리팩터링
```

- 테스트 작성 전 `.agents/domain/`의 객체, 행위, 속성, 불변식, 관계를 확인한다.
- 테스트가 검증할 규칙을 먼저 명확히 한다.
- 구현 세부사항이 아니라 외부에서 관찰 가능한 행위를 검증한다.
- 하나의 테스트는 하나의 규칙이나 의미 있는 시나리오를 검증한다.
- 테스트가 실패한 원인이 요구사항인지 구현 오류인지 구분한다.

## Aggregate와 불변식

도메인 테스트는 Aggregate 내부 객체부터 Root Aggregate 순서로 작성한다.

```text
내부 객체 불변식
        ↓
Root Aggregate 불변식
        ↓
Application 외부 불변식
```

- Entity와 Value Object의 고유 규칙은 단위 테스트로 검증한다.
- Root Aggregate는 내부 객체를 포함해 Aggregate 전체의 일관성을 검증한다.
- 여러 Aggregate, 저장소, 다른 모듈의 정보가 필요한 규칙은 Application 테스트에서 검증한다.
- Aggregate 내부 객체를 직접 변경하지 않고 Root Aggregate의 행위를 통해 검증한다.

## 테스트 종류

### 단위 테스트

작은 단위의 규칙과 흐름을 외부 기술 없이 검증한다.

- Domain 객체와 Aggregate
- Value Object
- Domain 규칙 객체
- Application Usecase의 분기와 협력 흐름

Application 테스트에서는 다른 모듈 API, Persist Repository, Infra Client 등을 테스트 대역으로 대체할 수 있다.

### 통합 테스트

실제 구성 요소의 협력과 기술 동작을 검증한다.

- Persist와 데이터베이스의 저장·조회
- 트랜잭션과 롤백
- 동시성 및 잠금
- Infra Client와 외부 통신 구성
- Presentation과 Spring MVC 구성
- Scheduler, Listener 등 Spring 실행 환경에 의존하는 기능

단위 테스트로 충분히 검증할 수 있는 분기까지 무거운 통합 테스트로 작성하지 않는다.

### 계약 테스트

모듈이나 외부 시스템 사이의 API 계약을 검증한다.

- 다른 모듈의 공개 API 입력과 반환 계약
- 외부 API 요청 형식과 응답 형식
- 계약에 정의된 오류와 실패 결과

## 계층별 테스트 방향

### Domain

- 외부 기술 없이 단위 테스트를 작성한다.
- 하위 객체의 규칙부터 Root Aggregate의 규칙 순서로 구현하고 검증한다.
- 상태 변화뿐 아니라 불변식이 위반되지 않았는지도 검증한다.
- 예외가 발생하는 경우 상태가 변경되지 않았는지 확인한다.

### Application

- Usecase의 실행 흐름과 분기를 단위 테스트로 검증한다.
- 다른 모듈 API, Repository, Infra Client는 테스트 대역으로 격리한다.
- 입력에 따라 올바른 협력 객체를 호출하는지 검증한다.
- 트랜잭션의 실제 동작, 롤백, 저장소 정합성은 통합 테스트로 별도 검증한다.
- 전체 애플리케이션 컨텍스트 로딩은 필요한 경우에만 사용한다.

### Persist

- Repository의 저장·조회 동작을 실제 데이터베이스로 검증한다.
- Entity 매핑, JPQL, JDBC, fetch join의 동작을 검증한다.
- 변경 조회 시 Aggregate Root와 필요한 하위 객체가 의도한 방식으로 조회되는지 확인한다.
- 동시성, 잠금, 트랜잭션이 중요한 경우 실제 데이터베이스 환경에서 검증한다.

### Infra

- 실제 외부 서비스 대신 MockServer 등 대체 서버를 사용한다.
- 실제 Client를 사용해 URL, Method, Header, Body를 검증한다.
- 정상 응답, 오류 응답, 타임아웃, 응답 지연을 검증한다.
- 외부 API 명세와 요청·응답 모델의 호환성을 계약 관점에서 검증한다.

### Presentation

- Controller의 입력 변환, Usecase 호출, Response 변환을 검증한다.
- 요청 검증과 예외 응답 형식을 검증한다.
- Scheduler, Listener, Consumer는 실행 조건이나 분기 로직이 있을 때 단위 테스트를 작성한다.
- Spring의 실제 이벤트 전달, 스케줄 실행, 비동기 동작이 중요하면 통합 테스트로 검증한다.
- 단순히 Usecase를 호출하기만 하는 진입점은 중복 테스트를 만들지 않는다.

## 테스트 대역

- 테스트 대역은 외부 의존성을 격리할 때 사용한다.
- Mock의 반환값만 검증하지 말고 Usecase의 최종 상태와 결과를 함께 검증한다.
- 실제 기술 동작을 검증해야 하는 대상은 Mock으로 대체하지 않는다.
- 테스트 대역의 설정이 실제 계약과 어긋날 수 있음을 고려한다.

## 시간과 비동기

- 시간에 의존하는 로직은 `Clock`을 주입해 검증한다.
- 비동기 결과는 고정된 `Thread.sleep()`보다 조건 기반 대기를 사용한다.
- Scheduler의 실행 주기와 실제 비즈니스 로직을 분리한다.
- 분산 실행이나 중복 실행 방지는 실제 공유 저장소와 실행 환경을 고려해 검증한다.

## 테스트 작성 원칙

- 테스트 이름과 설명은 검증하는 도메인 행위를 표현한다.
- Given, When, Then 구조로 시나리오를 명확히 한다.
- 테스트 간 실행 순서와 공유 상태에 의존하지 않는다.
- 하나의 테스트에서 검증 범위를 과도하게 넓히지 않는다.
- 통과하는 것만으로 충분하지 않으며, 누락된 불변식과 경계 조건을 검토한다.
## 테스트 작성 구조

- 테스트 메서드에는 테스트 의도를 설명하는 한국어 `@DisplayName`을 작성한다.
- 테스트 본문은 `// given`, `// when`, `// then` 주석으로 준비·실행·검증 단계를 구분한다.
- 실행과 검증이 분리되지 않는 예외 테스트는 `// when & then`을 사용할 수 있다.
- 엔티티의 getter 검증은 Lombok getter(`getId()`, `getStatus()` 등)를 사용한다.
- 테스트 메서드와 `@DisplayName`은 구현 방식보다 검증하려는 도메인 규칙을 표현한다.
- 테스트는 불필요한 fixture/helper 메서드를 만들지 않고, 테스트 내부에서 필요한 객체를 직접 생성한다.
- 여러 테스트가 같은 객체를 사용하더라도 helper 추상화가 테스트 의도를 흐리면 직접 생성하는 방식을 우선한다.
- Aggregate Root 테스트에서는 내부 Entity의 생성·상태 변경을 Root의 행위 메서드를 통해 검증한다.
- 연관관계가 있는 Entity 테스트에서는 도메인 객체 연관관계를 직접 구성하고, ID 값만 임의로 주입해 관계를 표현하지 않는다.
- 테스트 범위는 구현 계층에 따라 선택한다.
  - Domain: 불변식, 상태 전이, Aggregate 행위
  - Application: Usecase 흐름, Port 호출, 실패 흐름
  - Persist: Entity 매핑, Repository 저장·조회, Flyway 통합
  - Presentation: 요청 검증, 응답 변환, 예외 매핑
- 모든 테스트를 동일한 방식으로 작성하지 않고, 대상 계층의 실제 책임을 검증한다.
