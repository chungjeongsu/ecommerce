# Flyway 마이그레이션 규칙

## 목적

Flyway를 사용해 데이터베이스 스키마의 변경 이력을 버전으로 관리하고, 개발·테스트·운영 환경에서 동일한 스키마를 재현한다.

이 문서는 데이터베이스 스키마와 마이그레이션의 기술 규칙을 정의한다.

- 도메인 객체의 행위와 불변식은 `docs/domain/`에서 정의한다.
- JPA Entity, Repository, Domain 변환 규칙은 [`internal/persist` 규칙](internal/persist/persist.md)에서 정의한다.
- Repository와 마이그레이션의 실제 동작 검증은 [`테스트 규칙`](../../testing/test.md)에서 정의한다.

## 적용 범위

- 데이터베이스 스키마 생성 및 변경
- 테이블, 컬럼, 인덱스, 제약조건 관리
- 스키마 변경에 필요한 데이터 변환

현재 프로젝트는 MySQL을 대상으로 하며, Flyway를 데이터베이스 스키마의 유일한 변경 수단으로 사용한다.

## 파일 위치

마이그레이션 파일은 다음 경로에 둔다.

```text
src/main/resources/db/migration/
```

예시:

```text
src/main/resources/db/migration/
├─ V1__create_product_tables.sql
├─ V2__create_inventory_tables.sql
└─ V3__add_order_expires_at.sql
```

마이그레이션 파일은 Java 패키지나 도메인 모듈의 `internal` 패키지 안에 두지 않는다. 파일의 논리적 소유 도메인은 파일명과 내용으로 명확하게 표현한다.

## 파일명 규칙

버전 마이그레이션은 다음 형식을 사용한다.

```text
V{version}__{description}.sql
```

- `V`는 대문자로 작성한다.
- 버전은 양의 정수로 작성하고, 프로젝트 전체에서 중복하지 않는다.
- 버전은 이미 적용된 버전보다 큰 값을 사용한다.
- 설명은 영문 소문자와 밑줄을 사용한다.
- 설명은 마이그레이션의 목적이 드러나도록 작성한다.
- 파일 인코딩은 UTF-8을 사용한다.

```text
V1__create_product_tables.sql
V2__add_product_status.sql
V3__create_inventory_reservations.sql
```

현재는 변경 이력이 명확한 버전 마이그레이션(`V...`)을 기본으로 사용한다. 반복 실행이 필요한 Repeatable Migration(`R...`)은 별도 요구사항과 사용 목적이 확정된 경우에만 도입한다.

## 마이그레이션 작성 시점

모든 도메인의 Entity 구현이 끝날 때까지 기다리지 않는다. 하나의 도메인 기능을 영속화할 수 있는 상태가 되면 해당 기능의 마이그레이션을 함께 추가한다.

권장 순서는 다음과 같다.

```text
도메인 규칙 및 테스트
        ↓
JPA Entity·Repository 매핑
        ↓
Flyway 마이그레이션
        ↓
Repository 통합 테스트
```

- 도메인 규칙이 확정되기 전에 스키마를 먼저 고정하지 않는다.
- Entity와 Repository 매핑이 확인된 뒤 마이그레이션을 작성한다.
- Product, Inventory, Order, Payment 등 기능 단위로 마이그레이션을 나눈다.
- 서로 독립적인 변경을 하나의 파일에 무리하게 합치지 않는다.
- 하나의 마이그레이션은 하나의 논리적인 스키마 변경을 표현한다.

## 스키마 작성 규칙

- 테이블명과 컬럼명은 데이터베이스 명명 규칙에 맞는 `snake_case`를 사용한다.
- 도메인 불변식으로 보장되어야 하는 값은 가능한 범위에서 데이터베이스 제약조건으로도 보호한다.
  - 필수 값: `NOT NULL`
  - 중복 금지 값: `UNIQUE`
  - 참조 무결성: `FOREIGN KEY`
  - 허용 범위: 데이터베이스가 지원하는 경우 `CHECK`
- 데이터베이스 제약조건만으로 도메인 규칙을 대체하지 않는다.
- 인덱스는 실제 조회·변경 유스케이스를 근거로 추가한다.
- Entity의 컬럼 정의와 마이그레이션의 컬럼 정의가 서로 다르지 않도록 한다.
- 다른 모듈의 내부 Entity나 Repository를 기준으로 스키마를 설계하지 않는다.
- 외래키가 Aggregate 생명주기와 모듈 경계를 과도하게 결합하는 경우에는 먼저 설계를 확인한다.
- 외래키는 연관관계가 있다고 추가하지 않는다.
- 외래키는 대부분 쓰지않으나 사용자가 직접 언급할 시 추가한다.

## JPA와의 관계

Flyway가 스키마를 관리하므로 JPA가 스키마를 자동 변경하도록 설정하지 않는다.

- 기본 정책은 `spring.jpa.hibernate.ddl-auto=validate`로 한다.
- `create`, `create-drop`, `update`는 공유 데이터베이스나 운영 환경에서 사용하지 않는다.
- 스키마 변경은 Entity 수정만으로 완료하지 않고, 반드시 새 Flyway 마이그레이션을 추가한다.
- 애플리케이션 시작 시 Entity와 실제 스키마의 불일치를 검출할 수 있어야 한다.

## 변경 이력 관리

적용이 완료된 마이그레이션 파일은 수정하지 않는다.

```text
잘못된 방식: V3__create_order_tables.sql 수정
올바른 방식: V4__alter_order_tables.sql 추가
```

- 이미 공유 환경에 적용된 파일의 SQL을 변경하지 않는다.
- 기존 컬럼이나 데이터를 변경해야 하면 새로운 버전 파일로 처리한다.
- 마이그레이션 이력 테이블인 `flyway_schema_history`를 수동으로 수정하지 않는다.
- 컬럼 삭제, 타입 변경, 테이블 삭제처럼 복구가 어려운 변경은 영향 범위와 데이터 보존 방법을 먼저 검토한다.
- 파괴적인 변경은 애플리케이션 호환성을 고려해 단계적으로 수행한다.

## 데이터 변환

스키마 변경에 반드시 필요한 데이터 변환은 해당 마이그레이션에 포함할 수 있다.

- 데이터 변환의 대상과 목적을 SQL 또는 주석으로 명확히 한다.
- 변환 전후의 데이터 조건을 확인한다.
- 변환에 실패해도 기존 데이터가 손상되지 않도록 조건을 제한한다.
- 단순 초기 테스트 데이터나 개발 편의용 데이터는 버전 마이그레이션에 포함하지 않는다.
- 운영 데이터에 영향을 주는 변환은 별도의 검토와 검증을 거친다.

## 검증 규칙

마이그레이션을 추가하거나 변경한 경우 다음을 확인한다.

- 빈 데이터베이스에서 모든 마이그레이션이 순서대로 실행되는지 확인한다.
- 애플리케이션이 마이그레이션 완료 후 정상적으로 시작되는지 확인한다.
- `ddl-auto=validate` 환경에서 Entity와 스키마가 일치하는지 확인한다.
- Repository 통합 테스트가 실제 마이그레이션으로 생성된 스키마를 사용하는지 확인한다.
- 기존 마이그레이션을 다시 실행하거나 중복 버전이 발생하지 않는지 확인한다.
- 제약조건과 인덱스가 관련 유스케이스의 저장·조회 동작을 방해하지 않는지 확인한다.

## 리뷰 체크리스트

- [ ] 파일 위치가 `src/main/resources/db/migration/`인가?
- [ ] 버전이 중복되지 않고 기존 버전보다 큰가?
- [ ] 파일명이 `V{version}__{description}.sql` 형식인가?
- [ ] 하나의 논리적 변경만 포함하는가?
- [ ] Entity 매핑과 컬럼 정의가 일치하는가?
- [ ] 필요한 `NOT NULL`, `UNIQUE`, `FOREIGN KEY`, `CHECK` 제약조건을 검토했는가?
- [ ] 인덱스 추가 근거가 있는가?
- [ ] 적용된 기존 파일을 수정하지 않았는가?
- [ ] 빈 데이터베이스와 통합 테스트 환경에서 실행을 확인했는가?
- 이 프로젝트는 Aggregate 간 결합과 운영 중 마이그레이션 부담을 줄이기 위해 DB 외래키를 기본적으로 생성하지 않는다.
- 도메인 내부 연관관계는 JPA `@ManyToOne`, `@OneToMany(mappedBy = ...)`로 표현하고, 참조 무결성은 Aggregate와 Application 규칙으로 보장한다.
- 외래키가 반드시 필요한 예외적인 경우에는 구현 전에 요구사항과 운영 영향을 확인한다.
