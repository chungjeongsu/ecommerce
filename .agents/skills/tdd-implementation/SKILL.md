## Boundary

### Always

- 구현을 시작하기 전에 `.agents/architecture/architecture-directory.md` 본문을 반드시 읽는다.
- `architecture-directory.md`가 참조하는 Architecture 문서는 현재 변경 범위에 해당하면 이어서 읽는다.
- 모듈 간 의존성, 공개 API, `api/internal` 경계가 포함되면 `.agents/architecture/conventions/spring-modulith.md`를 추가로 읽는다.
- 폴더 구조와 클래스 배치는 `architecture-directory.md`를 우선 기준으로 판단한다.
- `.agents/domain/`, `.agents/architecture/`, `.agents/testing/`의 관련 규칙을 적용한다.
- 작업 시작 전에 필요한 문서 목록을 확정한다.
- 필수 문서는 본문을 끝까지 읽고 읽은 경로를 기록한다.
- 읽지 못했거나 일부만 읽은 필수 문서가 있으면 구현을 시작하지 않는다.
- 요구사항과 불변식을 필수 규칙과 선택 규칙으로 분류한다.
- 각 필수 규칙을 테스트, 구현 또는 검증 항목에 연결한다.
- 구현 후 문서 목록과 핵심 규칙을 다시 확인한다.
- 관찰 가능한 행위와 도메인 불변식을 테스트로 먼저 명세한다.
- 실패 테스트, 최소 구현, 리팩터링의 TDD 주기를 유지한다.
- 기존 사용자 변경과 요청 범위 밖의 코드를 보존한다.

### Ask First

- 구현에 필요한 도메인 규칙이나 생명주기가 확정되지 않은 경우
- 요청 범위를 넘어선 구조 변경이나 공개 계약 변경이 필요한 경우
- 데이터 삭제, 기존 마이그레이션 수정 등 복구하기 어려운 변경이 필요한 경우
- 관련 없는 기존 테스트 실패를 수정해야 진행할 수 있는 경우

### Never

- 테스트를 통과시키기 위해 도메인 규칙을 약화하거나 우회하지 않는다.
- 실패 테스트를 확인하지 않고 구현 코드를 먼저 작성하지 않는다.
- 요청과 무관한 리팩터링이나 의존성 변경을 함께 수행하지 않는다.
- 검증되지 않은 구현을 완료된 것으로 전달하지 않는다.

## Input Contract

- 구현할 사용자 요청과 확정된 범위
- 적용할 도메인 규칙, 불변식 및 사용자 결정
- 구현에 필요한 필수 문서 목록과 문서 로딩 결과
- 누락·모호·충돌 사항이 해소되었다는 분석 결과
- 이전 노드가 식별한 관련 코드 또는 기술 제약이 있다면 해당 정보

입력 형식은 제한하지 않지만 확정 사항과 미해결 사항을 구분할 수 있어야 한다.

## Responsibilities

- 변경이 영향을 주는 모듈, 계층, 공개 계약과 테스트 범위를 식별한다.
- 필요한 문서와 reference를 식별하고 읽은 경로를 기록한다.
- 요구사항과 불변식을 필수 규칙별로 분해한다.
- 각 필수 규칙에 대응하는 테스트와 검증 항목을 정의한다.
- 요구사항과 불변식을 표현하는 실패 테스트를 작성하고 실패 이유를 확인한다.
- 테스트를 통과시키는 최소한의 구현을 수행한다.
- 모든 필수 규칙이 테스트 또는 코드에 반영되었는지 대조한다.
- 테스트가 유지되는 범위에서 구조와 가독성을 개선한다.
- 관련 테스트와 필요한 빌드·정적 검증을 실행해 회귀 여부를 확인한다.
- 구현 결과를 원문 요구사항과 다시 대조한다.
- 구현 결과와 검증 상태를 후속 작업이 판단할 수 있게 정리한다.

## Output Contract

구현 결과를 독립적으로 검증할 수 있도록 아래 정보를 전달한다.

- 구현한 행위와 변경 범위
- 추가·수정한 코드와 테스트
- 읽은 필수 문서와 적용한 핵심 규칙
- 요구사항·규칙과 테스트·구현의 대응 결과
- 적용한 도메인 및 아키텍처 규칙
- 실행한 검증과 결과
- 남은 위험, 미해결 사항 및 수행하지 않은 범위
- 구현 완료 여부와 후속 작업에 필요한 조건

## Verification Gate

- [ ] 요구사항을 표현하는 테스트가 구현 전에 실패했는가?
- [ ] 최소 구현 후 관련 테스트가 통과하는가?
- [ ] 필수 문서의 본문을 끝까지 읽고 경로를 기록했는가?
- [ ] 모든 필수 규칙이 테스트, 구현 또는 검증 항목에 연결되었는가?
- [ ] 테스트 통과와 요구사항 충족을 별도로 확인했는가?
- [ ] 구현 결과를 원문 요구사항과 다시 대조했는가?
- [ ] 도메인 불변식과 아키텍처 경계를 지켰는가?
- [ ] 요청 범위 밖의 변경이 포함되지 않았는가?
- [ ] 검증 결과와 미해결 사항을 정확히 전달했는가?

하나라도 충족하지 못하면 구현 완료로 전달하지 않는다.

## Failure Policy

- 미확정 도메인 결정이 발견되면 구현을 중단하고 필요한 결정을 보고한다.
- 필수 문서를 읽지 못하면 구현을 중단하고 누락된 경로를 보고한다.
- 필수 규칙을 테스트, 구현 또는 검증 항목에 연결하지 못하면 구현을 완료하지 않는다.
- 원문 요구사항과 결과를 대조하지 못하면 완료로 보고하지 않는다.
- 테스트 실패 원인이 구현에 있으면 범위 안에서 수정하고 다시 검증한다.
- 테스트가 통과해도 요구사항이 누락되었으면 구현을 완료하지 않는다.
- 환경 또는 기존 결함으로 검증할 수 없으면 원인과 확인된 범위를 전달한다.
- 파괴적 변경이나 범위 확대가 필요하면 사용자 확인 전까지 대기한다.

## Exit Criteria

- 완료: 필수 문서를 읽고 모든 필수 규칙을 구현·검증한 뒤 Output을 전달했다.
- 대기: 사용자 결정이나 추가 권한이 필요하다.
- 실패: 문서 로딩, 규칙 반영, 구현 또는 필수 검증을 완료할 수 없다.
- 취소: 사용자가 구현을 취소했다.
