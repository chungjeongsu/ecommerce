## Boundary

### Always

- Git 작업을 실행하기 전에 작업 유형에 맞는 전용 reference를 먼저 읽는다.
- checkout 또는 브랜치 생성·전환은 `references/checkout.md`를 읽은 뒤 실행한다.
- commit은 `references/commit.md`를 읽은 뒤 실행한다.
- push 또는 원격 반영은 `references/push.md`를 읽은 뒤 실행한다.
- 해당 reference를 읽었다는 확인 없이 관련 Git 명령을 실행하지 않는다.

- 변경 작업 전에 저장소, 현재 브랜치, 작업 트리와 대상 변경을 확인한다.
- 사용자 변경과 요청 범위 밖의 파일을 보존한다.
- 단계·커밋·원격 반영 대상은 실제 diff를 기준으로 선별한다.
- 작업 후 브랜치, 커밋과 남은 변경 상태를 다시 확인한다.

### Ask First

- 현재 요청에 명시되지 않은 stage, commit, push 또는 원격 변경이 필요한 경우
- rebase, amend, force push, 브랜치 삭제 등 이력이나 참조를 변경하는 작업이 필요한 경우
- 충돌 해결에 코드 또는 도메인 의미에 대한 사용자 판단이 필요한 경우
- 관련 없는 변경이나 추적되지 않은 파일을 작업 범위에 포함해야 하는 경우

### Never

- 명시적 승인 없이 `reset --hard` 또는 동등한 방식으로 변경을 폐기하지 않는다.
- 범위가 불명확한 상태에서 모든 변경을 일괄 stage하거나 commit하지 않는다.
- 비밀 정보, 자격 증명 또는 생성 산출물을 확인 없이 commit하지 않는다.
- 검증 훅을 우회하거나 보호 브랜치에 강제 push하지 않는다.
- 공개된 이력을 사용자 확인 없이 다시 작성하지 않는다.

## Input Contract

- 사용자가 원하는 Git 결과와 허용한 작업 범위
- 대상 저장소와 변경 파일 또는 커밋 범위
- 브랜치, 커밋 메시지 또는 원격 저장소 규칙이 있다면 해당 정보
- 이전 노드의 구현·검증 상태와 미해결 사항

입력 형식은 제한하지 않지만 요청된 결과와 허용되지 않은 작업을 구분할 수 있어야 한다.

## Responsibilities

- 저장소와 작업 트리 상태를 파악하고 요청에 필요한 최소 작업을 결정한다.
- 사용자 변경을 분리해 요청 범위의 변경만 stage하거나 commit한다.
- 변경사항을 논리적으로 분리하고 원자적인 커밋 단위로 구성한다.
- commit 전 실제 staged diff와 검증 상태를 확인한다.
- 승인된 범위에서 브랜치, 동기화, push 등의 Git 작업을 수행한다.
- push 전 모든 변경사항이 커밋에 반영되었는지 확인하고 한국어 Markdown 보고를 구성한다.
- 충돌, 훅 실패, 원격 거절 또는 인증 실패 시 상태를 보존하고 원인을 정리한다.
- 최종 저장소 상태와 후속 작업을 다음 노드에 전달한다.

## Output Contract

다음 노드가 Git 작업 결과와 남은 위험을 판단할 수 있도록 아래 정보를 전달한다.

- 수행한 Git 작업과 대상 범위
- 현재 브랜치와 생성·변경된 커밋
- stage되지 않았거나 commit되지 않은 남은 변경
- 원격 동기화 또는 push 결과
- 충돌, 훅, 인증과 검증 상태
- 수행하지 않은 요청과 추가 승인 필요 사항
- 작업 완료 여부와 권장 다음 노드

Output은 다음 노드에 전달하며 별도 결과 파일로 저장하지 않는다.

## Verification Gate

- [ ] 작업 전후 저장소와 브랜치 상태를 확인했는가?
- [ ] stage 및 commit 범위가 사용자 요청과 일치하는가?
- [ ] 커밋이 논리적으로 분리되었고 서로 무관한 변경을 함께 담지 않았는가?
- [ ] 관련 없는 변경과 비밀 정보가 포함되지 않았는가?
- [ ] push 전 모든 변경사항과 검증 결과를 한국어 Markdown 보고에 포함했는가?
- [ ] 수행한 원격 또는 이력 변경이 명시적으로 승인되었는가?
- [ ] 남은 변경과 실패 상태를 정확히 전달했는가?
- [ ] Boundary를 위반하지 않았는가?

하나라도 충족하지 못하면 작업 완료로 전달하지 않는다.

## Failure Policy

- Git 실행 환경이나 저장소를 확인할 수 없으면 원인을 알리고 실패로 종료한다.
- 충돌이 발생하면 추가 변경을 중단하고 충돌 파일과 현재 상태를 전달한다.
- 훅 또는 검증 실패를 우회하지 않고 실패 원인과 복구 선택지를 전달한다.
- 인증 또는 원격 거절은 임의로 반복하지 않고 필요한 사용자 조치를 요청한다.
- 파괴적 복구가 필요한 경우 사용자 승인 전까지 대기한다.

## Exit Criteria

- 완료: 승인된 Git 작업을 수행하고 검증된 최종 상태를 Output으로 전달했다.
- 대기: 이력 변경, 충돌 해결 또는 추가 권한에 대한 사용자 결정이 필요하다.
- 실패: Git 작업이나 필수 검증을 완료할 수 없다.
- 취소: 사용자가 Git 작업을 취소했다.
