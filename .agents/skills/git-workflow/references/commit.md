# Commit 컨벤션

## 메시지 형식

커밋 메시지는 다음 형식을 사용한다.

```text
{type}: {한글로 작성한 변경 설명}
```

허용하는 `type`은 다음과 같다.

- `feat`: 사용자 기능 추가 또는 변경
- `chore`: 설정, 문서, 도구와 같은 부수 작업
- `refactor`: 외부 동작을 유지하는 구조 개선
- `fix`: 결함 수정
- `test`: 테스트 추가 또는 변경

변경 설명은 한글로 작성하고, 커밋이 실제로 바꾼 내용을 구체적으로 표현한다.

예시:

```text
feat: 주문 취소 가능 상태 추가
fix: 결제 승인 중복 요청 방지
refactor: 재고 예약 유스케이스 책임 분리
test: 주문 만료 상태 전이 테스트 추가
chore: 에이전트 워크플로 문서 정리
```

## 커밋 단위

- 서로 다른 목적의 변경사항을 하나의 커밋에 담지 않는다.
- 쪼갤 수 있는 범위 내에서 최대한 분리한다.
- 각 커밋은 가능한 한 하나의 논리적 변경사항만 포함한다.
- 기능 코드, 테스트, 문서, 설정이 서로 독립적이면 각각 분리한다.
- 한 변경을 완성하는 데 강하게 결합된 테스트와 구현은 하나의 단위로 묶을 수 있다.
- 단순히 파일 수를 줄이기 위해 의미 없는 커밋을 만들지 않는다.

## 실행 기준

1. 전체 diff를 읽고 변경사항의 목적을 분류한다.
2. 서로 다른 목적의 파일을 커밋 단위별로 나눈다.
3. 필요한 파일만 stage하고 staged diff를 확인한다.
4. 커밋 메시지의 type과 한글 설명이 staged diff와 일치하는지 확인한다.
5. 커밋 후 커밋 내용과 남은 변경을 확인한다.

범위를 안전하게 나눌 수 없거나 파일 하나에 서로 다른 변경이 섞여 있으면 임의로 커밋하지 않고 사용자에게 확인한다.
