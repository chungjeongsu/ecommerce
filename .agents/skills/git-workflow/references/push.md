# Push 컨벤션

## Push 전 확인

- 현재 브랜치와 대상 원격 브랜치를 확인한다.
- 작업 트리에 커밋되지 않은 변경이 남아 있는지 확인한다.
- 요청한 모든 변경사항이 커밋에 반영되었는지 확인한다.
- 최근 커밋의 파일과 내용을 실제 diff 기준으로 읽는다.
- 필요한 테스트, 빌드, 정적 검증과 리뷰 결과를 확인한다.
- push하지 않은 로컬 커밋과 원격 브랜치의 차이를 확인한다.
- 비밀 정보, 불필요한 산출물과 요청 범위 밖의 변경이 없는지 확인한다.

확인되지 않은 변경이나 필수 검증 누락이 있으면 push하지 않는다.

## Push 보고

push 전 다음 형식의 한국어 Markdown 보고를 구성해 Output으로 전달한다.

```markdown
# Push 보고

## 수정/추가사항

### 코드

- {수정하거나 추가한 코드와 목적}

### 테스트

- {수정하거나 추가한 테스트와 검증 대상}

### 문서·설정

- {수정하거나 추가한 문서·설정과 반영 내용}

### Skill·Workflow

- {추가하거나 변경한 Skill·Workflow와 책임}

### 기타

- {그 밖의 변경사항}

## 검증

- 작업 트리 상태: {clean 또는 남은 변경}
- 커밋 반영 상태: {모든 변경 반영 여부와 확인 방법}
- 테스트: {실행한 테스트와 결과, 없으면 사유}
- 빌드·정적 분석: {실행 결과, 없으면 사유}
- 리뷰: {검토 내용과 결과}
- 문서·규칙: {확인한 문서와 일관성 결과}
- 보안·범위: {민감 정보와 범위 밖 변경 확인 결과}

## 미해결 사항

- {없으면 `없음`}
```

보고에는 실제 변경된 내용과 추가된 내용을 구분해 기록하고, 코드·테스트·문서·설정·Skill·Workflow 변경을 빠짐없이 포함한다.
검증에는 작업 트리, 커밋 반영 여부, 테스트, 빌드·정적 분석, 리뷰, 문서 일관성, 보안·범위 확인 결과를 포함한다.
해당하지 않는 항목도 생략하지 않고 `해당 없음`과 사유를 기록한다.

## 실행 기준

1. Push 전 상태와 변경 누락 여부를 확인한다.
2. 변경사항과 검증 결과를 읽고 한국어 Markdown 보고를 작성한다.
3. 사용자에게 보고 내용을 전달하고, 추가 승인이 필요한 push인지 확인한다.
4. 승인된 원격에 push한다.
5. push 결과와 원격 상태를 다시 확인한다.

원격 저장소 변경이나 강제 push는 별도 승인이 없으면 수행하지 않는다.
