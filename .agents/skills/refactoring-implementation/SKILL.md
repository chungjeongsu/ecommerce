# Refactoring Implementation

## Boundary

### Always

- 리팩터링 대상과 보존할 동작을 먼저 확인한다.
- 관련 도메인·아키텍처·테스트 문서 본문을 읽고 경로를 기록한다.
- 변경 전 보호 테스트를 실행하고 기준 결과를 기록한다.
- 작은 구조 변경 후 관련 보호 테스트를 다시 실행한다.
- 변경 전후의 외부 동작과 공개 계약을 대조한다.
- 기존 사용자 변경과 요청 범위 밖의 코드를 보존한다.

### Ask First

- 보호할 외부 동작이나 공개 계약을 식별할 수 없는 경우
- 기존 테스트가 실패해 기준 상태를 확정할 수 없는 경우
- 아키텍처 규칙이나 공개 계약 변경이 필요한 경우
- 요청 범위를 넘어선 구조 변경이 필요한 경우
- 데이터 마이그레이션이나 파괴적 변경이 필요한 경우

### Never

- 새 기능을 추가하지 않는다.
- 도메인 규칙과 불변식을 변경하지 않는다.
- 데이터베이스 스키마를 변경하지 않는다.
- 테스트를 통과시키기 위해 기존 동작을 약화하지 않는다.
- 요청과 무관한 리팩터링이나 의존성 변경을 함께 수행하지 않는다.
- 검증되지 않은 구조 변경을 완료로 보고하지 않는다.

## Input Contract

- 리팩터링 목적과 확정된 범위
- 현재 코드 구조와 영향 범위 분석
- 목표 구조와 변경 책임
- 보존할 외부 동작, 공개 계약과 도메인 규칙
- 관련 보호 테스트와 기준 실행 결과
- 적용할 아키텍처·테스트 규칙

보존할 동작과 변경 범위를 구분할 수 있어야 한다.

## Responsibilities

- 보호 테스트가 보존할 동작을 충분히 검증하는지 확인한다.
- 보호 테스트가 부족하면 현재 동작을 명세하는 테스트를 추가한다.
- 구조 변경을 독립적으로 검증 가능한 작은 단위로 나눈다.
- 각 단위에서 구조와 책임만 개선한다.
- 각 변경 후 관련 테스트와 정적 검증을 실행한다.
- 변경 전후 공개 동작, 도메인 규칙과 데이터 계약을 대조한다.
- 구조 개선 결과와 잔여 위험을 정리한다.

## Output Contract

- 리팩터링 목적과 변경 범위
- 변경한 코드 구조와 책임
- 추가·수정한 보호 테스트
- 보존한 외부 동작, 공개 계약과 도메인 규칙
- 변경 전후 검증 결과
- 적용한 아키텍처·테스트 규칙과 근거 문서
- 범위 밖 변경, 잔여 위험과 미해결 사항
- 구현 완료 상태

## Verification Gate

- [ ] 변경 전 보호 테스트의 기준 결과를 확인했는가?
- [ ] 보존할 동작과 공개 계약을 식별했는가?
- [ ] 구조 변경을 작은 단위로 수행했는가?
- [ ] 각 변경 후 관련 테스트가 통과했는가?
- [ ] 외부 동작과 도메인 규칙이 유지되었는가?
- [ ] 데이터베이스 스키마와 데이터 계약이 유지되었는가?
- [ ] 요청 범위 밖의 변경이 포함되지 않았는가?
- [ ] 변경 결과와 미검증 범위를 정확히 기록했는가?

하나라도 확인하지 못하면 리팩터링 완료로 처리하지 않는다.

## Failure Policy

- 기준 테스트가 실패하면 원인과 기존 실패 여부를 확인하고 대기한다.
- 외부 동작이나 도메인 규칙 변경이 발견되면 리팩터링을 중단한다.
- Entity·스키마 변경이 필요하면 리팩터링을 중단한다.
- 구조 변경 후 테스트가 실패하면 해당 변경 범위에서 원인을 수정하고 다시 검증한다.
- 범위 안에서 동작을 복구할 수 없으면 변경 상태와 실패 원인을 보고한다.
- 실행할 수 없는 검증은 이유와 미검증 범위를 기록한다.

## Exit Criteria

- 완료: 외부 동작과 규칙을 보존한 구조 개선과 필수 검증을 완료했다.
- 대기: 동작 기준, 구조 결정 또는 추가 권한이 필요하다.
- 실패: 동작 보존, 구조 개선 또는 필수 검증을 완료할 수 없다.
- 취소: 사용자가 리팩터링을 취소했다.
