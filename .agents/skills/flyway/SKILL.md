## Boundary

### Always

- `.agents/architecture/conventions/flyway.md`를 스키마 변경과 마이그레이션의 기준으로 사용한다.
- 작업 전에 `src/main/resources/db/migration/`의 현재 버전과 대상 Entity 매핑을 확인한다.
- 테이블, 컬럼, 타입, 길이, nullable, 기본값, 인덱스, 제약조건과 연관관계의 변경 여부를 기준으로 마이그레이션 필요 여부를 판단한다.
- 스키마가 변경되면 기존 최대 버전보다 큰 새 버전 마이그레이션을 추가한다.
- 도메인 행위나 Java 접근 제어만 변경되어 스키마가 동일하면 마이그레이션을 추가하지 않고 판단 근거를 전달한다.
- Entity 매핑과 SQL 정의를 대조하고, 실행한 검증과 실행하지 못한 검증을 구분한다.

### Ask First

- 컬럼·테이블 삭제, 컬럼 타입 축소 또는 데이터 손실 가능성이 있는 변경이 필요한 경우
- 기존 데이터의 backfill, 변환 또는 정리가 필요한 경우
- 무중단 배포를 위해 여러 단계의 호환 마이그레이션 중 하나를 선택해야 하는 경우
- 외래키 추가가 필요한 경우
- 스키마 변경 요구와 Entity 매핑이 충돌하거나 도메인 규칙이 확정되지 않은 경우
- 관련 없는 기존 마이그레이션 실패를 수정해야 진행할 수 있는 경우

### Never

- 이미 적용되었거나 공유된 기존 마이그레이션 파일을 수정하지 않는다.
- 중복되거나 기존 최대 버전 이하인 버전을 새 마이그레이션에 사용하지 않는다.
- Entity 변경만으로 스키마 변경을 완료된 것으로 처리하지 않는다.
- `ddl-auto=create`, `create-drop`, `update`로 Flyway 마이그레이션을 대체하지 않는다.
- 도메인 문서에 없는 규칙을 데이터베이스 제약조건으로 확정하지 않는다.
- 사용자 결정 없이 외래키를 추가하지 않는다.
- 테스트 데이터나 개발 편의용 데이터를 버전 마이그레이션에 포함하지 않는다.
- 실행하지 않은 마이그레이션이나 검증을 통과한 것으로 전달하지 않는다.

## Input Contract

- 변경 대상 Entity와 Repository 또는 스키마 변경 요청
- 확정된 테이블·컬럼·제약조건과 데이터 보존 규칙
- 관련 도메인·아키텍처 결정
- 기존 마이그레이션과 적용 환경에 대한 정보
- 이전 노드에서 확인한 구현 및 테스트 상태가 있다면 해당 정보

입력 형식은 제한하지 않지만 확정된 스키마 변경과 미결정 사항을 구분할 수 있어야 한다.

## Responsibilities

- 변경된 Entity 매핑과 데이터베이스 영향 범위를 식별한다.
- 마이그레이션 추가 필요 여부와 근거를 판단한다.
- 현재 최대 버전 다음 번호와 `V{version}__{description}.sql` 형식으로 하나의 논리적 스키마 변경을 작성한다.
- 필수 값, 중복 금지, 허용 범위와 조회 경로를 근거로 필요한 제약조건과 인덱스를 검토한다.
- 기존 데이터가 있는 환경에서 변경 SQL의 호환성과 데이터 보존 위험을 확인한다.
- 빈 데이터베이스에서 전체 마이그레이션 실행, `ddl-auto=validate`, 관련 Repository 통합 테스트로 Entity와 스키마의 일치를 검증한다.
- 결과와 미검증 범위를 다음 노드가 판단할 수 있도록 정리한다.

구체적인 SQL과 검증 범위는 변경의 위험과 프로젝트 실행 환경에 맞게 결정한다.

## Output Contract

다음 노드가 스키마 변경의 완료 여부를 판단할 수 있도록 아래 정보를 전달한다.

- 변경된 Entity와 스키마 영향 범위
- 마이그레이션 추가 여부와 판단 근거
- 추가한 마이그레이션 버전, 파일과 논리적 변경 내용
- 제약조건, 인덱스와 데이터 변환 결정
- 실행한 마이그레이션·Entity validation·통합 테스트와 결과
- 데이터 호환성 위험, 미검증 범위와 사용자 결정 필요 사항
- 현재 작업 상태와 권장 다음 노드

Output은 다음 노드에 전달하며 별도 결과 파일로 저장하지 않는다.

## Verification Gate

- [ ] Flyway 기준 문서와 현재 마이그레이션 목록을 확인했는가?
- [ ] 변경된 Entity 매핑과 스키마 영향 범위를 모두 확인했는가?
- [ ] 마이그레이션 추가 또는 불필요 판단에 근거가 있는가?
- [ ] 새 버전과 파일명이 프로젝트 규칙에 맞는가?
- [ ] 적용된 기존 마이그레이션을 수정하지 않았는가?
- [ ] Entity 매핑과 SQL의 타입, 길이, nullable 및 제약조건이 일치하는가?
- [ ] 데이터 보존과 배포 호환성 위험을 검토했는가?
- [ ] 필요한 실행·validation·통합 테스트 결과와 미검증 범위를 구분했는가?
- [ ] Boundary를 위반하지 않았는가?

하나라도 충족하지 못하면 마이그레이션 작업을 완료로 전달하지 않는다.

## Failure Policy

- 도메인 규칙이나 스키마 계약이 미확정이면 마이그레이션을 작성하지 않고 필요한 결정을 요청한다.
- 기존 적용 파일의 수정이 요구되면 새 버전 마이그레이션으로 해결 가능한지 검토하고, 임의로 기존 파일을 변경하지 않는다.
- 데이터 손실이나 운영 호환성 위험이 있으면 영향과 대안을 전달하고 사용자 결정 전까지 대기한다.
- 마이그레이션 실행이나 Entity validation이 실패하면 우회하지 않고 실패 원인과 재현 범위를 전달한다.
- 실행 환경을 사용할 수 없으면 확인한 정적 일치 범위와 미검증 항목을 명시한다.

## Exit Criteria

- 완료: 마이그레이션 필요 여부를 근거와 함께 판단하고 필요한 SQL 작성과 검증을 완료했다.
- 대기: 스키마 계약, 데이터 보존 또는 파괴적 변경에 대한 사용자 결정이 필요하다.
- 실패: 필수 마이그레이션 작성이나 검증을 완료할 수 없다.
- 취소: 사용자가 Flyway 작업을 취소했다.
